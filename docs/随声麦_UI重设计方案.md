# 随声麦 UI 重设计方案

-   **文档版本：** 1.0
-   **文档类型：** UI/UX 设计与实现指导
-   **适用对象：** 随声麦 Windows 桌面应用
-   **设计目标：**
    在保留现有音频处理能力的前提下，提升界面清晰度、操作效率、状态可读性与视觉一致性
-   **依据说明：**
    本文基于用户提供的现有界面截图及已讨论的设计方向编写。当前尚未确认项目使用的
    UI
    框架、实际功能实现和设备状态，因此涉及具体技术实现的内容均以框架无关的设计规范或待确认事项表述。

------------------------------------------------------------------------

## 1. 项目概述

### 1.1 产品定位

随声麦是一款 Windows
桌面音频路由与音效控制工具。根据现有界面可见内容，应用涉及以下能力：

-   配置预设管理：切换、新建、复制、重命名、删除、保存。
-   音频发送与监听：真实麦克风、附加音频、应用音频以及监听功能。
-   音量与增益调节：监听音量、真实麦克风增益、应用增益、音效增益。
-   音效库管理：音效列表、播放、停止、导入、收藏/取回、删除等。
-   全局热键管理。
-   设备选择与相关设置。
-   紧急操作入口及运行状态提示。

以上清单只记录截图中可见或可合理识别的界面项目，不代表已经核实每项功能的内部行为。重构前应以代码和现有行为为准。

### 1.2 设计问题

现有界面主要存在以下可见问题：

1.  **信息层级不突出。**
    配置管理、运行状态、音频参数、音效列表和热键区域使用相似的视觉权重。
2.  **核心状态分散。**
    用户需要查看复选框、下拉框、状态标题和底部状态栏，才能判断各条音频路径的状态。
3.  **音效列表空间利用率偏低。**
    大面积列表区域只显示少量条目，单条音效缺少清晰的操作入口和元信息布局。
4.  **参数分组不够直观。**
    增益和监听音量集中排列，用户需要自行理解各项参数对应的音频路径。
5.  **控件风格偏传统。**
    默认控件、分隔线和紧凑排列较多，缺少统一的留白、尺寸和视觉规范。
6.  **底部状态信息难以快速扫描。**
    关键运行状态与其他文本混合，异常提示和普通状态之间的区分有限。

### 1.3 设计目标

-   让用户在打开窗口后数秒内判断应用是否就绪、哪些路径处于开启状态。
-   将高频操作放在容易发现的位置。
-   让每项音量参数与对应音频路径保持明确关联。
-   让音效库在只有少量或大量音效时都保持易读。
-   保留桌面工具的紧凑、高效特性，不设计成过度装饰的媒体播放器。
-   为后续深色模式、高 DPI、自适应窗口和可访问性留出规范。
-   以最小风险逐步替换界面，不在 UI 重构中顺带改写音频引擎。

### 1.4 非目标

第一阶段不要求：

-   重写音频处理、设备枚举或路由引擎。
-   增加未经验证的新音频功能。
-   添加复杂动效、3D 效果、动态背景或大面积渐变。
-   将所有功能都迁移到多页式设置中心。
-   为视觉效果牺牲低延迟、稳定性或系统资源占用。

## 2. 设计原则

### 2.1 状态优先

应用状态应比装饰更醒目。用户首先需要知道"当前是否工作"，其次才是可调整的参数。

### 2.2 功能就近

音量控制应放在相应音频路径内；音效操作应靠近音效条目；设备选择应靠近设备状态。

### 2.3 默认简洁，高级功能可展开

默认视图展示常用功能。较少使用的高级参数可放入折叠区域或独立设置弹层，但不应隐藏紧急操作或关键状态。

### 2.4 一致性优先于个别创意

相同含义的开关、按钮、状态标签、列表操作应采用一致的样式与行为。避免每个模块单独设计一套交互。

### 2.5 不以颜色作为唯一信息

开启、关闭、异常等状态应同时通过文字、图标或其他可识别元素表达。颜色只作为辅助提示。

### 2.6 渐进式重构

先建立布局和样式系统，再逐个迁移模块。每个阶段都应能够运行、测试和回退。

## 3. 信息架构

建议采用单主窗口结构。首屏分为以下区域：

1.  **顶部应用栏**
    -   应用图标与名称
    -   当前配置选择器
    -   配置管理入口
    -   紧急静音入口
2.  **运行状态摘要**
    -   音频引擎/应用整体状态
    -   真实麦克风状态
    -   应用音频状态
    -   监听状态
    -   设备异常或热键异常提示
3.  **音频路由控制区**
    -   真实麦克风
    -   应用音频
    -   监听输出
    -   音效输出/音效混音
4.  **音效库**
    -   搜索
    -   收藏筛选
    -   导入
    -   音效列表
    -   播放进度或播放状态（如果底层能力支持）
5.  **全局热键摘要**
    -   已绑定快捷键的简要状态
    -   设置/编辑入口
    -   未绑定或冲突提示
6.  **底部状态栏**
    -   音频引擎状态
    -   当前输出/输入设备摘要
    -   热键服务状态
    -   诊断日志入口（如已有日志能力）

## 4. 布局与窗口规范

### 4.1 窗口尺寸

建议先以以下范围进行设计和测试：

-   **推荐默认尺寸：** 960 × 760 DIP 左右。
-   **建议最小尺寸：** 760 × 640 DIP
    左右；最终数值应由实际控件、字体和内容决定。
-   **默认状态：**
    记住用户上次的窗口尺寸与位置（如应用已有持久化设置机制）。
-   **高 DPI：** 使用框架支持的 DPI
    缩放方式，避免以固定物理像素强行布局。
-   **窄窗口：**
    音频控制卡片从双列切换为单列；顶部配置区允许压缩或将次要操作合并进菜单。
-   **宽窗口：**
    限制内容最大宽度或合理增加列宽，避免列表文字被拉得过散。

以上是初始设计目标，应在真实应用上验证，不是硬性平台标准。

### 4.2 间距系统

采用 4/8 像素节奏，建议主要使用 8 的倍数：

  场景              建议间距
  -------------- -----------
  图标与文字            8 px
  同组控件之间          8 px
  卡片内边距           16 px
  卡片之间         12--16 px
  分区之间         20--24 px
  主窗口边距       16--24 px
  列表行内边距     10--12 px

实现时应优先使用布局容器的间距和内边距，不要依靠大量绝对坐标定位。

### 4.3 对齐规则

-   所有分区标题左边缘对齐。
-   同一行的按钮高度一致。
-   状态标签在同类组件中使用统一高度和内边距。
-   音量标签、滑块和数值控件尽量对齐。
-   列表中的名称、时长、收藏和更多操作使用固定的列结构。
-   避免通过空格字符实现排版。

## 5. 视觉设计系统

### 5.1 色彩

建议先实现浅色主题，并为深色主题预留语义化颜色变量。

  语义       浅色主题建议值   使用范围
  ---------- ---------------- --------------------------
  主背景     `#F7F8FA`        主窗口背景
  卡片背景   `#FFFFFF`        内容卡片、列表容器
  次级背景   `#F1F3F5`        次级控件、悬停区域
  主文字     `#1F2937`        标题和正文
  次级文字   `#6B7280`        描述、辅助说明
  分隔线     `#E5E7EB`        细分隔线、边框
  主色       `#2563EB`        主操作、选中状态
  主色悬停   `#1D4ED8`        主按钮悬停
  成功       `#15803D`        正常、已连接
  警告       `#B45309`        需要注意但仍可工作的状态
  错误       `#B91C1C`        故障、不可用、危险操作
  禁用文字   `#9CA3AF`        不可操作控件

这些色值是设计起点。实现后应检查文本对比度、禁用状态辨识度和不同显示器上的可读性。不要将成功绿用作所有开启按钮的固定颜色；颜色应表达语义，而非单纯装饰。

### 5.2 字体与字号

建议采用系统 UI 字体，避免引入不必要的外部字体文件。

  文本层级           建议字号 字重
  --------------- ----------- --------------
  应用名称          18--20 px 半粗体
  主分区标题        16--18 px 半粗体
  卡片标题          14--16 px 半粗体
  正文/控件文字     13--14 px 常规
  辅助说明          12--13 px 常规
  状态摘要          12--14 px 常规或半粗体

中文环境可优先使用系统默认中文 UI 字体；Windows
下可评估微软雅黑、Microsoft YaHei UI
或框架默认字体。应避免在一个窗口内混用过多字体和字重。

### 5.3 圆角与边框

-   卡片圆角：8--12 px。
-   按钮圆角：6--8 px。
-   输入框圆角：6 px 左右。
-   状态标签圆角：采用轻微圆角或胶囊形，但全局统一。
-   边框：1 px 细边框为主。
-   阴影：默认尽量不用；仅在弹层或浮层需要层级时谨慎使用。

如果所用框架不支持圆角或阴影，应优先保证间距、颜色、字体和对齐一致，不要为了模拟视觉效果引入不稳定的绘制逻辑。

### 5.4 图标

-   选择一套统一的线性图标体系。
-   常见含义：麦克风、应用窗口、耳机、音频波形、播放、停止、收藏、搜索、键盘、设置、警告。
-   图标默认尺寸建议 16--20 px。
-   图标按钮必须具有工具提示或可访问名称。
-   避免同一功能在不同区域使用不同图标。
-   不能仅用图标表达具有风险的操作，必须配有明确文字或确认机制。

## 6. 顶部应用栏与配置管理

### 6.1 布局

左侧放应用图标与名称，中部或右侧放当前配置选择器，右侧保留主要操作：

-   当前配置下拉框
-   配置管理菜单或按钮
-   全部静音/紧急静音按钮

当窗口较窄时，可将新建、复制、重命名、删除、保存等次要操作收进"配置管理"菜单，避免顶部出现过多同等重要的按钮。

### 6.2 配置管理行为

  --------------------------------------------------------------------------------------------------------
  操作                                建议交互
  ----------------------------------- --------------------------------------------------------------------
  切换配置                            选择后按现有产品逻辑应用；若可能覆盖未保存修改，应先提示

  新建                                打开轻量对话框，要求输入配置名称

  复制                                以当前配置为基础复制，自动给出可编辑名称

  重命名                              行内编辑或对话框，校验空名称与重名

  删除                                二次确认，明确说明删除对象；不允许删除系统强制保留的配置（若存在）

  保存                                保存当前配置；保存成功后给出短暂提示

  未保存修改                          显示未保存标记，并明确切换配置时的处理方式
  --------------------------------------------------------------------------------------------------------

不要假设现有程序一定存在"未保存修改"概念。若底层配置系统没有这一机制，应在实现前先确定数据模型和保存语义。

### 6.3 紧急静音

"紧急全"这一现有文案含义不够明确。若该按钮的真实行为是立即关闭所有音频发送或输出路径，建议改为"全部静音"或"紧急静音"。

设计要求：

-   按钮与普通配置操作明显区分。
-   静音后显示清晰的已静音状态。
-   若再次点击会恢复原状态，应明确按钮行为；若不会恢复，则不要暗示可切换。
-   若可以恢复，恢复时应保留并还原触发前的各路径状态，而不是无条件开启所有路径。
-   提供可配置的快捷键（仅在现有热键架构允许时）。
-   在操作完成前不得提前显示成功状态；应以音频引擎实际反馈为准。
-   如果设备断开或引擎不可用，提示实际结果，不要只改变 UI 标记。

## 7. 运行状态摘要

### 7.1 目的

用户不应仅凭底部状态栏来判断程序是否正常工作。建议在顶部应用栏下方增加一条紧凑状态摘要。

### 7.2 建议字段

-   总体状态：就绪、初始化中、部分不可用、发生错误。
-   真实麦克风：开启/关闭/设备不可用。
-   应用音频：开启/关闭/未选择应用。
-   监听：开启/关闭/输出设备不可用。
-   音效：空闲/播放中/播放失败。
-   热键：已绑定/未绑定/存在冲突（如果能检测）。

不要一次性展示所有诊断信息。正常状态下保持简洁，异常状态出现时再展开详细信息。

### 7.3 状态语义

  状态           文字建议       表现建议
  -------------- -------------- ------------------------
  正常且空闲     就绪           中性或轻量成功提示
  初始化中       正在初始化     中性提示，可显示进度
  路径关闭       已关闭         灰色状态标签
  路径开启       已开启         文字加状态标记
  设备缺失       未检测到设备   警告提示与修复入口
  音频引擎故障   音频引擎异常   错误提示，提供诊断信息
  热键未绑定     尚未绑定       中性提示与设置入口
  热键冲突       快捷键冲突     警告提示与重新绑定入口

### 7.4 重要实现原则

UI
状态必须由真实业务状态驱动。不要在用户点击开关时直接将标签设为"已开启"，然后假定后台操作一定成功。建议区分：

1.  用户请求的目标状态；
2.  操作执行中；
3.  引擎或设备返回的实际状态；
4.  操作失败时的错误状态。

## 8. 音频路由控制区

### 8.1 总体布局

使用两列卡片布局，每张卡片只负责一条主要音频路径。窄窗口下切换为单列。

建议卡片统一包含：

1.  图标与名称；
2.  当前状态；
3.  核心开关或启用操作；
4.  与该路径相关的设备/应用选择；
5.  该路径的音量或增益控制；
6.  高级设置折叠入口（如有）。

避免在卡片里重复放置同一功能的多个开关，也不要把不同音频路径的参数混放在一个公共区域。

### 8.2 真实麦克风卡片

建议显示：

-   标题：真实麦克风
-   状态：已开启/已关闭/设备不可用
-   输入设备名称（如果程序支持枚举设备）
-   启用开关
-   输入增益
-   可选的输入电平指示（只有在底层能够提供可靠电平数据时才展示）

交互要求：

-   设备缺失时，保留卡片并明确显示异常，不要直接隐藏。
-   设备切换失败时，显示错误和重试入口。
-   增益数值应与实际配置一致。
-   如果增益允许负值或超出 0--1 范围，显示单位和可调范围，避免用户误解。

### 8.3 应用音频卡片

建议显示：

-   标题：应用音频
-   状态
-   当前目标应用或"未选择应用"
-   选择/更换应用入口
-   应用音频增益
-   必要时显示应用未运行、无法捕获或权限不足的提示

如果实际功能只是统一发送应用音频，而不是捕获指定应用，应以现有真实能力命名，不能因为设计稿而改变功能语义。

### 8.4 监听输出卡片

建议显示：

-   标题：监听输出
-   状态
-   监听设备
-   监听音量滑块
-   设备不可用时的提示

应明确区分"发送到虚拟麦克风"和"本地监听"。用户可能希望将声音发送给游戏语音软件，但不一定希望自己听到回放。UI
必须清晰表达两者不是同一件事。

### 8.5 音效输出卡片

建议显示：

-   标题：音效
-   当前播放状态
-   音效增益
-   正在播放的音效名称（如果支持）
-   停止播放入口（如果支持）

如果同一时间可以播放多条音效，可考虑显示播放数量或提供统一停止控制；如果引擎只允许单条播放，不要在界面上暗示支持多音轨混音。

### 8.6 滑块与数值输入

-   滑块适合快速调整，数值框适合精确输入。
-   同一参数的滑块和数值框必须双向同步。
-   显示合理精度，例如 `0.20`；精度应与底层配置一致。
-   如果数值没有物理单位，应使用明确标签，避免随意标注百分比或 dB。
-   数值超出允许范围时，应限制输入或给出明确错误提示。
-   若拖动时频繁更新引擎会造成爆音或性能问题，应使用节流或在拖动结束时应用；具体策略需根据音频引擎验证。
-   滑块必须支持键盘操作。

------------------------------------------------------------------------

## 9. 音效库

### 9.1 布局

音效库建议使用紧凑列表，而非为每个音效设计大型卡片。

顶部工具区：

-   分区标题"音效库"
-   搜索框
-   收藏筛选
-   导入音效按钮
-   可选的排序菜单

每行音效建议包含：

-   播放/停止按钮
-   音效名称
-   时长（仅当能准确获取时）
-   收藏操作（如果收藏功能存在）
-   更多菜单：重命名、查看信息、删除等（按现有功能取舍）

### 9.2 列表行状态

  状态       建议表现
  ---------- -------------------------------------------------
  普通       标准背景
  鼠标悬停   轻微背景变化
  当前播放   显示播放标记或进度（如果可获取）
  已收藏     收藏图标处于选中状态
  文件丢失   显示不可用提示及重新定位/移除入口（如果可实现）
  播放失败   显示错误提示，保留错误信息供诊断
  正在导入   显示导入进度或处理中状态（如果导入是异步操作）

### 9.3 搜索与筛选

-   搜索应至少覆盖音效名称。
-   搜索为空时显示"没有匹配的音效"，而不是空白区域。
-   空列表时显示引导文案，例如"尚无音效，导入音频文件以开始使用"。
-   收藏筛选只在实际存在收藏能力时提供。
-   搜索与筛选应能同时工作。
-   不要因为列表过滤而改变底层音效数据或删除文件。

### 9.4 导入流程

推荐流程：

1.  用户点击"导入音效"。
2.  打开系统文件选择器。
3.  依据当前实际支持的格式过滤文件。
4.  校验文件是否存在、是否可读取、格式是否受支持。
5.  对重复文件采用明确策略：跳过、覆盖或询问用户；不能静默覆盖。
6.  显示导入成功数量与失败原因。
7.  导入完成后将新条目加入列表，并保留原有列表选择逻辑。

支持的格式必须以现有音频库和实际测试结果为准，不要在 UI
中承诺未实现的格式。

### 9.5 删除操作

-   单条删除放入更多菜单。
-   删除前说明将删除的是列表记录还是磁盘文件。
-   如果会删除磁盘文件，必须明确告知并进行确认。
-   删除后更新列表焦点，避免焦点跳到不可预测的位置。
-   如果支持撤销，可以提供短暂撤销入口；如果没有实现撤销，不应显示虚假的撤销提示。

### 9.6 播放与停止

-   播放按钮在播放过程中应变为停止或显示相应播放状态，具体取决于引擎支持的控制方式。
-   连续点击不应造成重复启动或状态错乱。
-   若播放失败，显示可理解的错误信息。
-   若播放会发送至虚拟麦克风或其他外部目标，应在产品中明确该音效的路由去向。
-   不要仅在 UI 中改变播放图标而不检查后台播放状态。

------------------------------------------------------------------------

## 10. 全局热键

### 10.1 主窗口摘要

主窗口只展示热键概况，例如：

-   已绑定：显示最常用的快捷键摘要。
-   未绑定：显示"尚未绑定快捷键"。
-   存在冲突：显示冲突提示并提供设置入口。

详细热键列表可放入独立对话框或设置面板。

### 10.2 热键设置界面

建议字段：

-   功能名称
-   当前快捷键
-   重新录制/绑定
-   清除绑定
-   冲突状态
-   保存/取消

### 10.3 交互要求

-   进入录制状态后，显示"请按下组合键"。
-   显示已捕获的按键组合。
-   对重复绑定和系统保留键进行检测（前提是技术实现能够检测）。
-   检测失败或系统不允许注册时，显示明确原因。
-   用户取消录制时，保留原绑定。
-   不能在录制过程中误将普通按键输入到其他控件。
-   若应用支持热键持久化，重新启动后应恢复绑定状态。
-   对"全部静音"等高影响操作，应在设置中清楚说明快捷键效果。

------------------------------------------------------------------------

## 11. 设备与高级设置

"设备与"这一类不完整文案建议改成明确的"设备设置"或"设备管理"，具体名称由实际功能决定。

设备设置可包含：

-   输入设备选择
-   输出/监听设备选择
-   虚拟音频设备状态
-   设备重新扫描
-   设备切换失败提示
-   与设备相关的诊断信息

高级设置可折叠展示，例如：

-   高级增益参数
-   音频缓冲或延迟参数（如果已有）
-   音频引擎诊断
-   日志与调试选项

不要在没有充分说明的情况下暴露用户难以理解的底层参数。对可能导致声音中断、失真或设备不可用的选项，应提供说明和合理默认值。

------------------------------------------------------------------------

## 12. 底部状态栏与诊断信息

### 12.1 状态栏

建议保留一条较低视觉权重的状态栏，展示少量稳定信息：

-   引擎状态
-   设备连接摘要
-   热键服务状态
-   诊断信息入口

不要将所有参数、所有路径的详细状态都挤在状态栏中。

### 12.2 诊断面板

如果现有程序已有日志能力，可以提供一个独立的诊断面板，展示：

-   时间
-   事件类型
-   涉及的设备或路径
-   可读错误信息
-   可复制的详细信息

诊断信息应帮助定位问题，避免只显示"失败"而不提供任何上下文。日志中可能含有设备名称、应用名称或文件路径，导出前应提醒用户检查隐私信息。

------------------------------------------------------------------------

## 13. 交互反馈规范

### 13.1 按钮

-   主按钮：当前区域最重要的确认操作。
-   次按钮：普通操作，使用描边或中性样式。
-   危险按钮：删除、清除等破坏性操作使用明确危险样式，并尽可能放入菜单。
-   图标按钮：必须有工具提示和可访问名称。
-   禁用按钮：应说明不可用原因，或提供可理解的提示。

### 13.2 加载与异步操作

对于设备扫描、配置加载、导入音效等可能耗时的操作：

-   显示处理中状态。
-   防止重复提交。
-   在成功或失败后恢复可操作状态。
-   失败时保留用户已输入内容。
-   不要在后台操作尚未完成时显示成功状态。

### 13.3 提示消息

成功提示应简短，不打断用户的主要操作。错误提示应包括：

1.  发生了什么；
2.  对用户造成什么影响；
3.  下一步可以做什么。

避免只显示内部异常名称。详细技术信息可以放入诊断面板或复制信息中。

### 13.4 确认对话框

只在可能造成数据丢失、文件删除、配置覆盖或明显副作用时使用确认对话框。普通开关和音量调整不应频繁弹出确认。

------------------------------------------------------------------------

## 14. 可访问性与易用性

-   所有可操作控件均应支持键盘导航。
-   焦点状态清晰可见。
-   按钮和图标提供可访问名称。
-   文本与背景保持足够对比度。
-   不能只通过颜色区分状态。
-   滑块应支持方向键微调。
-   下拉框、弹窗和列表在键盘操作下保持合理焦点顺序。
-   高 DPI 下文字和图标不应模糊。
-   Windows 缩放比例为 100%、125%、150%、200% 时均应测试。
-   文本较长、设备名称较长或语言变化时，布局不能重叠。
-   如果应用支持系统深色模式，应统一处理主窗口、弹窗、文件选择器外的自绘控件与状态提示。

------------------------------------------------------------------------

## 15. 响应式布局策略

桌面软件的"响应式"重点是窗口尺寸变化时布局仍然清楚，而不是照搬网页布局。

### 宽窗口

-   音频卡片采用两列。
-   音效库占用剩余宽度。
-   配置管理操作可直接显示。

### 中等窗口

-   保留两列卡片，但减少卡片内次要文字。
-   配置管理中的低频操作收进菜单。
-   音效名称可使用省略号，但应提供完整工具提示。

### 窄窗口

-   音频卡片改为单列。
-   顶部工具区允许换行或收纳到菜单。
-   不应让滑块和数值输入框互相挤压。
-   音效列表保留播放、名称和更多操作，次要元信息可以隐藏。

如果采用传统桌面布局框架，应使用其布局系统、尺寸策略和锚定机制实现，而不是为每种窗口尺寸手工维护一套坐标。

------------------------------------------------------------------------

## 16. 建议的组件清单

在代码层面，可以将 UI
拆分为以下逻辑组件。具体类名和文件组织应遵循现有项目风格。

  组件                 职责
  -------------------- ----------------------------------
  MainWindow           主窗口、整体布局、窗口状态
  AppHeader            应用名称、配置选择、主要操作
  ProfileManager       配置切换与管理
  StatusSummary        汇总当前运行状态
  AudioRouteCard       单条音频路径的状态与控制
  GainControl          滑块、数值框、范围校验与同步
  SoundLibrary         音效搜索、筛选、列表
  SoundItemRow         单条音效的播放与管理操作
  HotkeySummary        热键摘要
  HotkeyEditor         热键录制、冲突检测与保存
  DeviceSettings       设备选择、刷新与错误状态
  DiagnosticsPanel     诊断信息与日志
  ConfirmDialog        统一确认弹窗
  Toast/Notification   轻量操作反馈
  ThemeTokens          颜色、间距、字体、圆角等设计变量

这些是职责划分建议，不要求机械地一项对应一个源文件。对于规模较小的项目，可以合并组件；对于复杂项目，则应保持业务逻辑与视觉组件分离。

## 17. 业务逻辑与 UI 的边界

UI 重构最重要的风险是意外改变音频行为。建议遵循以下边界。

### UI 层负责

-   展示当前状态；
-   收集用户输入；
-   进行基本输入校验；
-   发送用户操作请求；
-   展示操作进度、成功和失败；
-   组织控件布局和视觉样式。

### 业务/服务层负责

-   配置读取、保存与切换；
-   音频设备枚举和切换；
-   真实麦克风、应用音频、监听、音效路由；
-   音量和增益参数的应用；
-   热键注册与解绑；
-   音效加载、播放、停止、导入与删除；
-   向 UI 提供真实状态和错误信息。

### 必须保持的原则

-   UI 不应直接伪造业务成功状态。
-   不应在 UI 事件中复制一套音频状态。
-   同一状态应有明确的数据来源。
-   后台任务失败后，界面应回到真实状态。
-   配置持久化格式在 UI 改版期间尽量保持兼容。
-   若确需改变配置格式，应提供迁移、备份和回退方案。

------------------------------------------------------------------------

## 18. 技术实现建议

由于尚未确认应用框架，以下是框架无关的实现策略。

### 18.1 如果继续使用现有框架

优先评估能否通过以下方式完成重构：

-   统一主题变量；
-   使用布局容器替代绝对定位；
-   提取公共按钮、卡片、滑块和状态标签样式；
-   将主窗口拆分为逻辑区域；
-   通过状态模型统一更新控件；
-   使用原有业务接口执行音频操作。

不要为了追求圆角而一次性引入庞大的 UI 依赖。

### 18.2 如果项目使用 Qt / PySide / PyQt

可以评估：

-   使用布局管理器组织区域；
-   使用统一的 QSS 主题变量和控件样式；
-   将音频路径抽象为可复用控件；
-   通过信号与槽同步业务状态；
-   对耗时设备操作使用合适的异步/工作线程机制，避免阻塞 UI 线程。

这是条件性建议，只有在确认项目采用 Qt 系列框架后才适用。

### 18.3 如果项目使用 C# WinForms / WPF

可以评估：

-   WinForms：统一控件样式、使用布局容器，谨慎处理高 DPI 和自绘控件；
-   WPF：使用资源字典、样式、模板和绑定，尽量避免在代码中散落颜色和尺寸常量；
-   将业务服务与视图层分离，避免 UI 事件直接承载复杂音频逻辑。

这是条件性建议，需根据实际框架选择。

### 18.4 如果项目使用 Tkinter

可以评估：

-   使用统一的 ttk 样式；
-   用 Frame 划分功能区域；
-   避免依赖绝对坐标；
-   对无法自然实现的圆角效果保持克制，不要让视觉仿真增加维护成本。

### 18.5 不建议在框架未确认时做的事

-   直接指定新的 UI 框架并开始迁移；
-   将现有窗口整体推倒重写；
-   改动音频线程、设备生命周期和配置格式；
-   以大量自绘控件替代所有系统控件；
-   在没有测试的情况下增加动画或高频刷新。

## 19. 分阶段实施计划

### 阶段 0：现状盘点

任务：

-   确认 UI 框架和版本；
-   记录现有窗口、控件、事件处理与业务接口；
-   记录每个开关的真实含义；
-   确认各增益参数的单位、范围与持久化方式；
-   确认配置管理、音效导入/删除和热键的当前行为；
-   建立可运行的基线版本。

交付物：

-   当前功能清单；
-   现有行为记录；
-   UI 控件与业务接口对应表；
-   可回退的代码版本。

验收标准：

-   关键行为都有明确说明；
-   能够在重构后复现现有基本功能；
-   对不明确的行为已标注，而不是自行猜测。

### 阶段 1：基础视觉统一

任务：

-   统一字体、颜色、间距和控件高度；
-   统一按钮、输入框、状态标签样式；
-   减少不必要的分隔线；
-   调整窗口边距和区域标题。

验收标准：

-   相同类型控件外观一致；
-   没有文字重叠或控件裁切；
-   音频业务行为未发生变化。

### 阶段 2：重排主窗口

任务：

-   建立顶部应用栏；
-   增加运行状态摘要；
-   将音频参数按路径重新分组；
-   优化音效库列表；
-   将热键区域调整为摘要加设置入口；
-   整理底部状态栏。

验收标准：

-   用户可以快速识别主要路径状态；
-   每个参数与对应路径的关系明确；
-   窗口缩放后仍可正常操作；
-   原有功能入口均有明确去向。

### 阶段 3：交互与异常状态

任务：

-   统一加载、成功、失败和禁用状态；
-   处理设备缺失、切换失败、播放失败；
-   处理配置覆盖与删除确认；
-   处理热键未绑定和冲突；
-   检查紧急静音的真实行为与状态同步。

验收标准：

-   失败操作不会显示为成功；
-   异常状态有明确解释和下一步操作；
-   用户可以区分关闭、不可用和操作失败。

### 阶段 4：细节与兼容性

任务：

-   检查键盘导航；
-   检查高 DPI；
-   检查窗口最小尺寸；
-   检查长设备名和长音效名；
-   检查深色模式（如果计划支持）；
-   检查安装包中的图标和资源路径。

验收标准：

-   主要分辨率和缩放比例下布局稳定；
-   常用操作可通过键盘完成；
-   无明显的布局跳动、裁切或状态误导。

## 20. 测试清单

### 20.1 基础功能回归

-   [ ] 启动应用后状态与实际音频引擎一致。
-   [ ] 切换配置后各项参数正确更新。
-   [ ] 新建、复制、重命名、删除、保存行为与改版前一致。
-   [ ] 真实麦克风开关有效。
-   [ ] 应用音频开关有效。
-   [ ] 监听开关有效。

## 21. 验收标准与衡量指标

建议将验收分为四类。

### 视觉质量

-   控件尺寸、间距和字体统一；
-   主次操作层级清晰；
-   视觉装饰不干扰状态识别；
-   常见窗口尺寸下无明显布局问题。

### 操作效率

-   高频功能在主窗口中容易找到；
-   音量参数与目标路径明确对应；
-   音效播放、停止和导入步骤清晰；
-   配置管理不会因为按钮过多而挤压核心区域。

### 状态准确性

-   UI 展示的状态来自真实业务状态；
-   成功、失败、处理中和不可用有明确区分；
-   设备断开、热键冲突等问题能够被用户发现。

### 回归安全

-   现有音频路由能力保持不变；
-   配置兼容性得到验证；
-   不因 UI 更新引入音频中断、重复操作或热键失效；
-   异常路径均经过基本测试。

## 24. 推荐实施优先级

### P0：必须先做

-   统一状态语义；
-   将音量参数按音频路径分组；
-   明确紧急静音的含义；
-   保证 UI 状态与真实音频状态同步；
-   保护配置和音频功能不受视觉重构影响。

### P1：优先改善

-   统一视觉规范；
-   重排主窗口；
-   优化音效列表；
-   统一按钮和状态标签；
-   改善设备缺失、播放失败和热键未绑定等提示。

### P2：后续完善

-   深色模式；
-   更完整的诊断面板；
-   高级设置折叠；
-   更细致的键盘导航和可访问性优化；
-   可选的紧凑模式。

### P3：暂缓

-   大量动画；
-   复杂自绘效果；
-   不必要的页面切换；
-   与核心音频体验无直接收益的装饰性功能。

## 25. 最终建议

本次 UI
重设计的核心不是把传统控件简单换成圆角卡片，而是建立清楚的操作模型：

1.  **先看状态：** 当前应用和音频路径是否正常。
2.  **再选路径：** 真实麦克风、应用音频、监听输出和音效分别管理。
3.  **就地调整：** 参数紧贴对应路径，避免跨区域寻找。
4.  **集中管理音效：** 搜索、播放、收藏、导入和删除采用一致的列表交互。
5.  **异常可诊断：**
    设备、音频引擎和热键出问题时，给出准确状态和下一步操作。

建议先完成 P0 与
P1，再根据真实使用反馈决定是否扩展。尤其在开始编码前，应先确认当前 UI
框架、音频路径的真实定义、紧急静音行为以及配置持久化方式。这样可以把视觉重构的风险限制在
UI 层，而不是意外影响软件最重要的音频功能。
