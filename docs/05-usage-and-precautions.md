# Onbody Mic 使用说明与注意事项

版本：v1.0 文档基线（规划版）  
日期：2026-10-24  
状态：程序尚未实现；本文是未来首版的使用、安装和安全边界说明，不是已完成能力清单。

本文把已确认的使用目标与采用的安全默认值整理成一份可交接的操作手册。实现时若原型、设备或 KOOK 实测结果与本文不一致，必须先记录证据并更新本文，不能把规划行为描述成已实现能力。项目总需求见[产品需求与交互](01-product-requirements.md)，模块和信任边界见[模块架构与安全边界](02-architecture-and-safety.md)，阶段门槛见[路线图与验收计划](03-roadmap-and-acceptance.md)，事实来源和许可摘录见[来源与决策登记](04-sources-and-decisions.md)。

## 1. 阅读约定与当前边界

- **规划行为**：本文中“应当”“默认”“计划”表示 v1.0 设计基线，不表示当前已有可执行程序。
- **已知事实**：来自用户要求或来源登记中的 `[S01]`--`[S10]`；来源原文和限制以[04-sources-and-decisions.md](04-sources-and-decisions.md)为准。
- **待实测**：本机 Windows 版本、KOOK 版本、真实麦克风、耳机、播放器、浏览器、音频格式、延迟、热键和虚拟设备的实际组合均未在本项目中验证。
- **首发范围**：Windows 开发和 KOOK 优先；跨平台只保留模块边界，不承诺 macOS/Linux 已有音频后端或虚拟设备。
- **不做的事**：不自动录制通话、不上传音频、不改变 KOOK 私有设置、不通过模拟按键绕过游戏或反作弊、不默认捕获全系统声音。

## 2. v1.0 使用基线

以下默认值已按用户“按照建议来”的要求采用，并由项目协调者补充确定了开关语义。后续如需变更，应同步更新需求、架构和验收文档。

| 项目 | v1.0 默认行为 |
| --- | --- |
| 同时使用的来源 | 一个指定应用 + 一只真实麦克风 + 一条短音效；不默认扩展到多个应用 |
| 应用捕获粒度 | 单一应用/进程树；不承诺浏览器标签页或窗口级细分 |
| 发送开关 | 真麦发送、附加音频总开关、应用发送子开关；启动全部关闭 |
| 音效发送 | 无独立音效总开关；附加音频总开关开启后，用户主动触发音效才发送 |
| 应用发送 | 应用子开关必须开启，且附加音频总开关也开启才发送；打开应用子开关不会自动打开附加音频总开关 |
| 附加音频关闭 | 停止外发应用/音效并清除相关缓存，同时将应用发送子开关置为关闭并停止应用采集；已主动开始的本地试听不受影响；真麦发送独立 |
| 音效冲突 | 新音效替换正在播放的旧音效；同一条再次触发从头重播；不循环 |
| 按键触发 | 全局热键默认均未绑定，由用户自行设置；按住不因系统重复事件而连续播放 |
| 启动恢复 | 记住最后使用的预设，但真麦发送、附加音频、应用发送、监听全部关闭 |
| 预设切换 | 所有预设切换先停止音效、清空队列、关闭全部发送和监听；包括只改音量的预设。确认后仍由用户重新启用 |
| 监听偏好 | “仅音效”是监听模式偏好，不是启动时自动开启；主动开启监听时可优先选择该模式，也可显式切换到“实际虚拟录音端点全混音”检查 |
| 监听模式互斥 | “仅音效监听”和“实际端点全混音监听”绝不同时叠加 |
| 素材管理 | 导入时复制到受管音效库；不移动、覆盖或修改用户原文件 |
| 关闭窗口 | 首次关闭时说明仍在运行，随后进入托盘；托盘退出则停止全部本程序音频 |
| 紧急全静音 | 锁存关闭所有本程序发送和监听；明确解除后进入就绪静音，不恢复任何开关 |

主界面可以显示综合状态，但不额外设置第四个“隐藏必需总闸”。三个发送控件的关系必须始终可见：真麦独立；应用需要“附加音频总开关 + 应用子开关”；音效需要“附加音频总开关 + 用户触发播放”。关闭附加音频时，应用子开关必须被置为关闭并停止该应用采集；之后再次开启附加音频只恢复“可播放音效”，不会恢复应用发送。此时对应用发送的请求必须直接拒绝并提示用户先开启附加音频、再显式开启应用子开关，不能隐式打开任何开关。这些是产品行为约定，不代表已经实现或已通过设备验证。

## 3. 首次安装与配置（未来流程，不在本轮执行）

### 3.1 安装前准备

1. **确认系统和设备**：记录 Windows 版本/build、CPU 架构、KOOK 形态（建议优先测试桌面客户端）、常用浏览器/播放器、真实麦克风、耳机以及游戏权限级别。当前这些信息均为待实测项。
2. **准备隔离的测试内容**：使用自己制作的短脉冲或带明显标记的音频，不用真实通话内容做首轮隔离测试。准备一个目标应用和一个非目标应用，分别播放不同标记音。
3. **确认没有误以为“安装即完成”**：Onbody Mic 本身尚未实现；未来安装器能否携带虚拟音频端点取决于最终路线和许可，不应提前承诺自动安装驱动。
4. **不降低系统安全性**：安装和测试不要求长期管理员常驻、不要求关闭安全软件、不要求开启 `testsigning`。若某候选驱动提出这些要求，应暂停并重新评估，不以此掩盖路线问题。

### 3.2 虚拟音频端点（候选方案）

首版可评估独立安装现成虚拟音频线（例如 VB-CABLE），但它是候选依赖，不是本项目已经内置的驱动。官方资料说明其播放侧与录音侧方向为 `CABLE Input` -> `CABLE Output`，安装/卸载可能要求管理员运行并重启；具体步骤、版本和设备名以发布时官方说明为准 `[S02]`。

未来首次配置应遵循以下顺序：

1. 用户自行查看并同意候选虚拟设备的官方许可和安装说明。
2. 单独安装并重启（若官方安装器要求）；不要让 Onbody Mic 静默下载或替换系统驱动。
3. 在 Windows 设备列表中确认播放侧和录音侧均存在，并记录稳定设备标识。
4. 在 Onbody Mic 中把**写入端**明确设置为虚拟线播放侧，在 KOOK 中把**输入端**明确设置为虚拟线录音侧。
5. 不使用“跟随系统默认设备”作为隐含路由；设备失效时应安全停止，而不是自动改用另一只麦克风。

官方产品页未给出可作为本项目保证的排他写入承诺；规划不能假定虚拟线具有独占写入或旁路防护（来源与限制见 `[S02]`）。如果其他程序能直接写入同一播放端点，其声音可能绕过 Onbody Mic 的应用级选择开关而进入虚拟录音端点。项目不能声称能全面扫描或杜绝其他应用写入；这必须在 P0 中实际验证和如实说明。

### 3.3 Onbody Mic 未来首启向导

首启向导应按以下顺序让用户确认：

1. 选择真实麦克风（具体设备，不是模糊的“默认麦克风”）。
2. 选择虚拟输出写入端点和监听耳机/扬声器。
3. 选择一个应用作为本预设的唯一应用源，显示应用身份和“整应用/进程树范围”提示。
4. 导入一条短音效；程序校验可解码性、时长和大小，并复制到受管库，不修改原文件。
5. 为需要的动作设置热键；首次安装不替用户占用任何游戏键。热键冲突要显式报错；保留键（例如 F12）不应注册 `[S08]`。
6. 保存预设。保存只记录配置，不启动发送、监听或音效播放。
7. 在 KOOK 中手动选择虚拟录音端点，使用标记音和真实麦克风做本地/远端测试。不要在未经确认的公共频道中做首轮测试。

向导结束时应显示清晰的“已配置但未发送”状态。未来程序若不能验证输出端点，不得退回系统默认麦克风或全系统回环。

## 4. 推荐音频链路与 KOOK 配置

### 4.1 逻辑链路

```text
Selected app -> App sub-gate --+
Clip Send --------------------+-> Extras gate --+
Physical mic -> Mic gate -----------------------+-> Mixer / peak protection
                                                              |
                                                        Final safety gate
                                                              |
                                                       Virtual render endpoint
                                                              |
                                                       Virtual capture endpoint
                                                              |
                                                             KOOK

实际端点监听：虚拟录音端点 → 监听路由 → 耳机
仅音效监听：音效总线 ───────→ 监听路由 → 耳机
```

两种监听路径必须互斥。监听永远不能回到发送混音中，否则会形成软件内环路。真实扬声器还可能被真实麦克风再次拾音；这属于物理回声风险，程序不能保证消除。

### 4.2 KOOK 中的操作顺序

1. 打开 KOOK 语音设置，手动选择虚拟录音端点；不要依赖系统默认设备。KOOK 桌面客户端是首轮测试建议，不是用户当前形态或兼容性承诺。
2. 先保持真麦发送、附加音频总开关、应用发送子开关和监听均关闭，检查虚拟端点方向。
3. 只开启真麦发送，确认 KOOK 能收到讲话；之后如需发音效，开启附加音频总开关并主动触发音效；如需发应用声音，还必须单独开启应用发送子开关。
4. 在自由说话与按键说话两种 KOOK 模式中分别测试。Onbody Mic 不操控 KOOK 的 PTT、降噪、增益或自动门限，也不能保证音效绕过 KOOK 的语音门控。
5. 若 KOOK 自动调节增益、门限或处理音效，应按 KOOK 官方排错建议和实际测试记录调整 `[S07]`；不能把关闭所有安全处理作为通用解决方案。
6. 只有确认本地听感和测试接收端都正确后，才在实际开黑中使用。端点监听只能说明本机端点内容，不等于 KOOK 编码、网络和队友最终听感。

### 4.3 浏览器和应用来源警告

Windows 进程 loopback 的能力边界是进程及其子进程，不是网页标签页或窗口；官方样例还注明目标没有音频流时可能只是静音，并有最低系统 build 说明 `[S01]`。因此：

- 选择浏览器可能把该浏览器其他标签页、窗口或同一进程树的声音一起带入。
- 若 KOOK 网页版和音乐网页在同一浏览器，队友声音可能被捕获并回送；这是高风险组合，建议使用 KOOK 桌面客户端和独立音乐应用，或至少使用不同应用并做标记音测试。
- 应用退出、重启或同名程序出现时，不得自动改绑另一个实例；应提示用户重新确认。
- 本项目不能宣称“全面扫描所有应用并保证不混入”，也不能把系统全局回环当成单应用捕获的替代品。

## 5. 日常使用流程

### 5.1 开始开黑前

1. 启动程序，确认载入的是最后使用的预设。
2. 检查状态：真麦发送、附加音频总开关、应用发送子开关、监听。默认全部关闭；设备失效或预设不完整时保持静音。
3. 确认 KOOK 仍选择正确的虚拟录音端点。
4. 按按钮或用户自设热键逐项开启需要的来源；不需要发送的来源保持关闭。
5. “仅音效”只是监听模式偏好，不会在启动时自动打开监听；用户主动开启监听时可优先采用该模式。需要检查完整混音时，先关闭仅音效监听，再显式打开实际端点全混音监听。

### 5.2 播放音效

- 每条音效可在面板收藏、搜索、重命名和绑定一个用户自设热键；收藏是界面组织状态，不会把音效自动设为可发送。
- 热键是全局绑定，不随预设布局改变；当前布局未显示的音效也能在附加音频开启后被其明确绑定的键触发。设置页应列出全部生效绑定，删除音效/预设同步清理引用，避免误以为切预设就禁用了别的键。
- 热键只有在附加音频总开关开启且音效源有效时才会触发发送；关闭时不偷偷开总开关、不排队，也不在稍后补播。附加音频关闭时发起应用发送请求同样直接拒绝并提示，不得隐式开启总开关。
- 新音效会替换旧音效；同一音效再次触发会从头播放；不循环；按住不重复触发。另设“停止全部音效”动作。
- 本地试听与外发播放共用同一个音效播放器，但试听动作会替换当前正在外发的音效并切换到仅本地路径，绝不发送试听内容；真麦和应用发送状态不变。试听期间为避免重复，自动暂停“仅音效监听”和“实际虚拟录音端点全混音监听”；试听正常结束时可恢复试听前的监听模式。紧急全静音、停止全部音效、切换预设、设备失效或用户关闭监听都会取消该恢复，不得在之后自动重开。
- 音效文件失效、无法解码或超出限制时，显示错误并阻止触发，不用其他音效静默替代。

### 5.3 控制和紧急处理

| 操作 | 预期效果 |
| --- | --- |
| 真麦发送开关 | 独立控制真实麦克风，不依赖附加音频开关 |
| 附加音频总开关 | 允许/禁止应用和音效外发；关闭时停止外发应用/音效、清相关缓存并把应用子开关置为关闭、停止该应用采集；已主动开始的本地试听不受影响，不影响真麦 |
| 应用发送子开关 | 只有附加音频总开关也开启时才发送当前应用；关闭总开关后子开关为关闭，再次开启总开关不会自动恢复应用；总开关关闭时的应用发送请求必须拒绝并提示 |
| 播放音效 | 附加音频总开关开启后由用户主动触发；没有额外音效发送总开关 |
| 停止全部音效 | 停止当前音效、清空队列并停止本地试听；不打断讲话或应用背景音，也不关闭持续的实际端点全混音监听 |
| 监听关闭 | 只关闭本地监听，不改变 KOOK 已收到的发送路径 |
| 紧急全静音 | 锁存关闭所有本程序发送和监听并停止音效；明确解除后保持静音，设备有效才进入就绪，仍须逐项重开 |

紧急全静音是锁存安全状态。播放热键、切换预设、设备重新出现或程序恢复都不能自动解除它；解除后也不自动恢复任何音源或监听。

### 5.4 切换预设和退出

所有预设切换都先停止音效（包括本地试听）、清空旧队列、关闭真麦发送、附加音频、应用发送和监听，再校验新应用、设备和音效引用；即使预设只改变音量也执行相同安全关闭，并取消任何“试听结束后恢复监听”的待恢复标记。确认成功后进入“已配置但未发送”，由用户重新启用。切换失败时保持安全静音，不使用部分旧配置和部分新配置的混合状态。

启动只恢复最后预设的配置和界面选择，不恢复上一次正在说话、正在播放、正在监听的会话。关闭主窗口首次应说明“程序仍在托盘运行”；从托盘退出时要停止音频线程、清空缓冲并解除本程序热键，不留下后台续播任务。

## 6. 常见故障排查

以下步骤按“先看状态、再看方向、最后做端到端测试”的顺序执行。每次记录程序版本、Windows build、设备名/稳定 ID（可脱敏）、KOOK 形态和实际操作，不凭猜测改系统设置。

| 现象 | 先检查 | 安全处理与下一步 |
| --- | --- | --- |
| KOOK 完全没有声音 | KOOK 是否选择虚拟录音端点；真麦开关、附加音频开关、应用子开关是否符合预期；输出端点是否有效 | 不自动切换系统麦克风；用标记音分开测试真麦、音效、应用 |
| 只有讲话没有音效 | 附加音频总开关、热键是否绑定、音效文件是否可解码 | 总开关关闭时热键不排队；检查面板状态和受管库文件 |
| 只有音效没有讲话 | 真实麦克风设备、真麦发送开关和权限/断连状态 | 只恢复经过确认的真实麦克风，不改变应用或系统默认设备 |
| 应用声音没有进入 | 目标应用是否仍是已确认实例、应用子开关和附加音频总开关是否都开启、是否正在发声 | 不改捕获为全系统回环；提示重新绑定并记录未验证边界 `[S01]` |
| 混入其他浏览器网页/KOOK 声音 | 是否把 KOOK 和音乐放在同一浏览器进程树 | 立即关闭附加音频；更换为 KOOK 桌面客户端+独立音频应用并重测 |
| 声音重复、回声或啸叫 | 是否同时开启两种监听；应用原声是否已在耳机播放；是否使用扬声器 | 两种监听模式不能同时开；优先耳机；关闭监听不会改变发送路径 |
| 音效明显被截断或听不见 | KOOK 自由说话/按键说话、降噪、门限、自动增益 | 记录 KOOK 设置和端点实际内容；不能宣称可绕过 KOOK 处理 `[S07]` |
| 按住热键连续播放 | 是否误用重复触发、是否与游戏或其他程序冲突 | 使用防重复注册和明确冲突提示；不注入游戏；更换用户自设组合键 |
| 重启后突然有声音 | 这不符合 v1.0 基线；核对是否误把预设保存当作恢复会话 | 立即紧急全静音并提交脱敏诊断；这是安全缺陷，不是正常行为 |
| 切换预设后残留旧声音 | 是否执行了停止、清队列和发送关闭 | 立即紧急全静音；这是需要修复并重新验收的缺陷，不应以重启掩盖 |
| 本地端点有声、队友听不到 | KOOK 输入端点、KOOK 发言门控/处理和网络接收测试 | 本机监听不代表远端结果；按 KOOK 设置逐项核对 `[S07]` |

## 7. 安全、隐私与许可注意事项

### 7.1 发送边界和误传风险

- **已送出的声音不可追回**：本程序的静音只能阻止后续样本；已经进入 KOOK 或被队友听到的内容无法撤回。因此首次测试必须用无敏感标记音，并先确认目标频道/接收者。
- **共享虚拟线可能旁路**：第三方虚拟设备不一定只接受 Onbody Mic 写入；其他应用直接向其播放侧写声可能绕过本程序的选择开关 `[S02]`。不能声称本软件能全面扫描或杜绝其他应用写入端点。
- **应用捕获不是网页捕获**：浏览器进程可能承载多个来源；同浏览器运行 KOOK 网页和音乐有回送风险 `[S01]`。
- **物理回声不受数字静音完全控制**：扬声器声音可能被真实麦克风拾音；优先使用耳机。软件不能保证消除声学反馈。
- **端点监听不是远端验收**：KOOK 自身的语音处理、编码、网络与接收设备会改变最终听感 `[S07]`。
- **异常必须保守处理**：设备、进程或路由状态不明确时关闭相关发送；不允许静默回退到全系统混音、默认麦克风或其他应用。

### 7.2 系统安全和驱动

- 不要求管理员身份长期运行应用；如候选虚拟设备的官方安装/卸载流程需要提升权限，应由用户明确启动官方安装器，并在安装前看清发布者和来源 `[S02]`。
- 不要求禁用驱动签名、关闭安全启动、安全软件或系统保护，也不要求开启 Windows `testsigning`。若候选路线依赖这些操作，暂停并重新评估；不要照着未经核实的网络教程操作。
- 首版不应把自研虚拟驱动当成默认依赖。微软 SysVAD 是样例，不是可直接交付的完整混音驱动；驱动签名和分发有独立流程 `[S09][S10]`。
- 卸载虚拟音频设备前，确认没有其他应用或设备配置依赖它。卸载只针对明确安装的目标组件；不删除共享运行库、不清理不明驱动、不移除其他虚拟设备。
- 安装或卸载若需要重启，应先保存工作并遵照设备供应方文档；本项目不能保证第三方驱动的卸载影响范围。

### 7.3 隐私与日志

- 规划基线是不录制、不保存、不上传真实通话和麦克风内容。若未来需要录制、云同步或诊断上传，必须作为新的明确功能单独获得用户授权，说明保存位置、保留期限、删除方法和传输对象。
- 诊断日志只记录必要状态、错误码、时间和脱敏设备标识；默认不记录完整窗口标题、音频内容、聊天内容或用户音效文件内容。
- 用户主动导出日志前，应显示将包含的字段并允许取消。日志不应自动附带音频录制、缓存波形或媒体文件。
- 导入音效会在未来复制到受管本地音效库；用户应确认自己有权使用和传播该素材。删除库内副本不应删除原始文件，也不应删除预设外的其他文件。
- 本地试听与外发播放必须有清晰、不同的操作提示，避免把私密素材误发给语音频道。

### 7.4 素材许可

用户负责确认导入音效的版权、授权范围和语音频道使用规则。个人持有文件不自动意味着可以公开传播或分发。项目不能提供法律结论，也不应随安装包附带未经许可的音效素材。

候选虚拟设备、音频库、UI 框架及其许可证应在具体版本和分发方式确定后重新核查。VB-CABLE 的分发条件依使用模式而异，不能概括成“永远禁止捆绑”或“可无条件捆绑”；发布前按官方许可复核 `[S03]`。组件选择和版本也有变化可能，开发开始和正式发布前都复核来源登记 `[S03][S04][S05][S06]`。
