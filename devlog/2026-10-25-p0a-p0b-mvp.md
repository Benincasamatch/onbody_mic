## 2026-10-25（下午追加）：免驱动虚拟麦路线成立，无需 VB-CABLE

用户指令："我不想使用 vb-cable，先尝试不需要这个的方法"。本轮未安装任何软件、未使用管理员权限。

### 修正上午的错误结论

上午"本机无可用的免驱动数字通路"的结论**错误**：8 组合矩阵只覆盖了活动端点。Steam Streaming Speakers 驱动的 capture 端点（`内部 AUX 插座`，wave/Software_IO 桥接引脚，单声道 44.1kHz/32bit float）处于**软禁用**状态（MMDevice `Disabled`，注册表 DeviceState=0x10000001 带隐藏位），不出现在枚举里，因此完全没被测到。

### 发现与启用链（全部事实）

1. `devices --all` + 注册表 `HKLM\...\MMDevices` 直读确认该端点存在且为 Disabled；同时确认本机**无任何 Stereo Mix** 端点（Senary/Odo/NVIDIA 驱动均不暴露）。
2. 新增 `OnbodyMic.Platform.Windows/WindowsEndpointControl.cs`：未公开 `IPolicyConfig` COM 接口（SoundSwitch 等广泛使用的 vtable 布局）调用 `SetEndpointVisibility` 启用端点——等价于 mmsys.cpl 里点"启用"，按用户生效、无需提权。启用后端点变 **Active**。
3. `IPolicyConfig::SetDeviceFormat` 在本 build（26300）两个变体上均返回 0x88890008（连"设回当前格式"也拒）→ 引擎共享格式不可程序化修改。
4. 替代方案：**独占模式**以 44100Hz/16bit/立体声直接打开 Steam render pin（`loop --share exclusive --rate 44100 --bits 16`），与 capture pin 的 44.1kHz 对齐，绕过引擎 48kHz 混合格式。

### 实测证据（CLI 命令行输出留档于 `.tools/tmp/`，仓库不入库）

| 实验 | 结果 | 判定 |
| --- | --- | --- |
| 捕获端空闲 3s 基线 | rms=0.000000 | 纯数字静音，无环境声混入 |
| 共享模式 48k 播 440Hz | 频谱主峰 404Hz = 440×44100/48000 | 证实驱动 render→capture 数字直通、仅速率不匹配 |
| 独占 44.1k 播 440Hz（`loop_excl_44k16.wav`） | tone-detected，tone/noise=4,538,411，onset 521ms（含 500ms 预启动 → **链路约 21ms**） | **数字回环成立** |
| mixloop：真麦缓冲→MediaFoundationResampler 44.1k→与 440Hz 混合→独占写 render，同时从 capture 端点取证（`mixloop.wav`） | tone-detected，ratio=3,240,969，onset 352ms（含 300ms 预热 → **约 52ms** 含重采样启动） | **T03 原型：真麦+音效混合可送入虚拟麦** |

### 限制与边界（后续必须处理）

### 2026-10-25（夜）追加：断续根因 = MediaFoundationResampler 速率失配；已换 WDL 修复

现象链：`--monitor local` 首测自声音延迟 ~1s（用户实测）；加抖动控制后延迟受控但语音断续（用户实测）。

根因（数字证据）：麦克风引擎格式 48kHz/2ch/float（probe_mic.wav 头部实证），`MediaFoundationResampler` 在 48k→44.1k 转换中按输出速率消费输入，每秒净积压 ~81ms（= 麦缓冲 2s 上限内涨到 ~1s 延迟的来源）；修剪线程每秒丢弃 ~81ms 语音（8%）即断续。**该 bug 影响送入 KOOK 的主干人声**（此前 KOOK 听到的语音即带 ~8% 降调+断续）。

修复：麦克风链路改 `WdlResamplingSampleProvider(44100)`（纯托管、比率明确）；cable 监听改 `MonoToStereoSampleProvider`（44.1k→44.1k 升混，去掉多余 MFT）。实测：discard 从 ~81ms/s 降至 0-9ms/s（启动首秒 165ms 为预期突发修剪），麦缓冲 8-80ms 浮动不再钉死，线缆侧 tone-detected 保持。

遗留：抖动控制（TrimTo/TrimSinks，40ms 周期，目标 80/60ms）保留为长期保险；`discard_ms_per_s` 持续打印为产品指标原型（P1 应作为脱敏指标上报）。用户主观音质/延迟确认进行中。

### 2026-10-25（深夜）追加：T04/T05 单应用隔离验证通过（per-process loopback）

实现（`ProcessLoopbackCapture.cs`，约 300 行自写 interop，移植微软 ApplicationLoopback 样例）：

- `ActivateAudioInterfaceAsync("VAD\Process_Loopback", IID_IAudioClient, VT_BLOB(AUDIOCLIENT_ACTIVATION_PARAMS))` + 托管完成回调；接口 IID 与 vtable 顺序对照 mingw-w64 `mmdeviceapi.h` 与 NAudio main 分支核实（均 IUnknown 布局，无 IInspectable 槽位）。
- 捕获格式 44.1kHz/2ch/16bit PCM，`LOOPBACK|EVENTCALLBACK|AUTOCONVERTPCM`；SILENT 标志帧写零。
- CLI `proloop --pid <n> [--mode include|exclude]`；`devices` 增加 `*` 默认设备标记（本机默认输出=扬声器 Odo、默认输入=头戴式麦克风 Odo）。

实测（两独立 dotnet 进程分别播 700Hz/1200Hz 至默认设备，互为干扰源）：

| 用例 | 结果 |
| --- | --- |
| T04：捕获 700Hz 进程树，1200Hz 并发 | 700Hz tone-detected（ratio 1.67×10^7）；1200Hz no-tone（ratio 0.10）——非目标完全不可见 |
| T05：静音进程对照（双音仍并发） | rms=0.000010——无任何泄漏 |

结论：**进程树级隔离成立**，未选应用在受控链路内不可见（P0B 门槛第 3 条满足）。剩 T06（真实浏览器双标签页边界，需用户配合）、T08（应用重启重绑，P1）。
